# نتائج Benchmark حقيقية (مُقاسة فعلياً، وليست مُختلَقة)

قياسات مُلتقَطة فعلياً أثناء تطوير هذا الإصدار، على جهاز تطوير Linux
(Ubuntu 24.04، g++ 13). أعد التشغيل بنفسك عبر `benchmarks/benchmark.sh
<مجلد>` — الأرقام أدناه **قابلة لإعادة الإنتاج** بنفس المدخلات تقريباً (فروق
طفيفة ممكنة حسب إصدار zlib/zip المُثبَّت).

## 1. مكتبة Rin حقيقية بالكامل (23 ملف `.og.rin`، 193.20 KB أصلياً)

المصدر: `lib/*.og.rin` من مستودع RinLang الفعلي — نصوص كود بحتة، بلا أي
تكرار ملفات (0 dedup).

| الأداة | الحجم الناتج | نسبة الضغط |
|---|---|---|
| **CLC (level 2)** | 66,221 bytes | 65.7% |
| **CLC (--ultra)** | 66,137 bytes | 65.8% |
| zip -9 | 66,784 bytes | 65.4% |
| tar.gz | **54,064 bytes** | **72.0%** |

**الملاحظة الصادقة**: CLC أفضل من `zip -9` القياسي بفضل قاموس الرموز
المشترك (§9 في FORMAT.md) — لكنه أسوأ من `tar.gz`. السبب: `tar.gz` يضغط كل
الملفات الـ23 **كتدفّق واحد متواصل (solid)**، فيستفيد DEFLATE من التكرار
عبر حدود الملفات بالكامل (نفس أسماء الدوال، نفس الكلمات المفتاحية، نفس بنية
التعليقات تتكرر بلا حدود كتلة تفصل بينها). CLC (مثل ZIP) يضغط كل ملف/كتلة
**منفصلة** عمداً — التبرير والمقايضة موثَّقان في `docs/FORMAT.md` §13 وفي
README (§القيود الحالية، البند 2): هذا يمكّن `clc extract` لملف واحد بلا فك
المشروع كاملاً، وstreaming بذاكرة محدودة. **الحل المقترَح للنسخة القادمة**:
"Solid Block Mode" اختياري لمستوى `--ultra` تحديداً (تُشرَح المقايضة بالضبط
في نفس القسم).

## 2. مجموعة ملفات مختلطة الأنواع (33 ملف، 684.30 KB) — الحالة الواقعية

Rin (.og.rin) + JSON + HTML + JS + XML + Markdown + CSV + **صور PNG حقيقية**
(من `assets/branding/` في مستودع RinLang، غير قابلة للضغط أكثر أصلاً — وهذا
بالضبط سيناريو "لا تعِد ضغط ما هو مضغوط أصلاً" من المتطلبات).

| الأداة | الحجم الناتج | نسبة الضغط |
|---|---|---|
| **CLC (level 2)** | 474,131 bytes | 30.7% |
| **CLC (--ultra)** | 473,953 bytes | 30.7% |
| zip -9 | 475,547 bytes | 30.5% |
| tar.gz | 468,872 bytes | 31.5% |

هنا الفارق يتقلّص كثيراً (CLC يتفوّق على zip، ويقترب جداً من tar.gz) لأن
الصور (~420 KB من أصل 684 KB) تهيمن على الحجم الكلي ولا تستفيد أي أداة من
"solid compression" عليها أصلاً (بيانات شبه عشوائية بعد ضغط PNG الداخلي) —
راجع تفصيل نسبة كل ملف على حدة أدناه.

### تفصيل نسبة الضغط لكل نوع ملف (من `clc list` فعلياً)

| النوع | مثال | نسبة ضغط CLC |
|---|---|---|
| JSON | `database.rules.json` | 83.2% |
| كود Rin | `bob.og.rin` | 74.2% |
| HTML | `index.html` | 61.5% |
| Markdown | `README.md` | 51.4% |
| CSV | `sample.csv` | 27.5% |
| XML | `locales_config.xml` | 37.9% |
| JS | `rin.js` | 57.2% |
| **PNG (صورة حقيقية)** | `icon_green_master.png` | 21.6% |
| **PNG (صورة حقيقية)** | `icon_black_master.png` | **16.4%** |

هذا يطابق ما طُلب صراحة في §15/21: **لا ادّعاء بضغط 10MB→10KB**، والصور لا
تُعاد "ضغطها بشكل غير منطقي" — النسبة المنخفضة على PNG (16–22%) هي بالضبط
ما تبقّى فعلياً بعد أن ضغطها PNG نفسه سابقاً؛ CLC لم يفشل، بل قاس الواقع
بصدق (ولم يخزّنها STORE خالصاً لأن DEFLATE ما زال يجد فائدة صغيرة حقيقية).

## 3. زمن الحزم (Packing Time)

كلا القياسين أعلاه: **أقل من 50 ميلي ثانية** على الجهاز المذكور (0.021–0.044
ثانية) — لا حاجة لـ benchmark زمني منفصل عند هذا الحجم؛ الأرقام مطبوعة تلقائياً
في خرج `clc pack` نفسه لأي مشروع.

## كيفية إعادة إنتاج هذه الأرقام

```bash
./build.sh
./benchmarks/benchmark.sh /path/to/any/real/project
```
